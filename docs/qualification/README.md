The suite is pinned to upstream commit `461b40267aabd644558f9b19dbb9507dd5f691cf` and npm conformance package 0.3.7. Historical load profiles with four writers, eight streams, and 16 readers assign each writer to one fixed stream: eight readers receive data and eight are idle connections. Their byte/digest checks include the expected empty histories. They qualify those workloads, not 16 readers receiving every append. New reports expose the writing-stream and active/idle-reader counts, and the manual workflow defaults to four streams so all 16 readers receive writes. Compare this mapping as well as connection count when comparing runs.

Current focused evidence includes 49 unit/property tests, 75 integration/Neon cases, nine actually deployed Function cases (including three public HTTPS webhook tests), two cron-free deployed hint cases, and a real WAL-LSN child-branch recovery drill. `2026-11-22-load-smoke.json` records a **20-second probe**, using a Node.js client in London against a deployed Function in `aws-eu-central-1`, Postgres compute configured for 0.25–1 CU, pool maximum five, four writers, sixteen live readers, eight binary streams, and 1 KiB records. It acknowledged and then replayed 1,009 unique records after sealing, with no observed errors. Append p50/p95 were 69.87/81.10 ms; observed live p50/p95 were 86.30/99.25 ms. The report includes the exact deployed bundle hash. Other qualification Functions shared the account.

The ten-minute baseline in `2026-11-22-load-600-baseline.json` acknowledged and replayed **38,360 records**, about **63.93 appends/second**, through 16 live readers and 144 SSE rotations. There were no observed request errors, missing records, duplicates, or producer-order failures. Append p95 was 75.93 ms; observed live p95 was **4.43 seconds**. During writes the recovery-only worker accumulated **274 frozen chunks, 31.1 MB of local payloads, and 18,912 pending changes**. Explicit post-load maintenance drained them before replay. Connection counts went from 11 to 18 and include other branch activity; this is not yet an explanation of per-instance pool behavior.

This is a passing **data-safety probe**, with a demonstrated **maintenance-capacity gap**. It does not qualify steady-state operation: the example's old eight-chunk/16-change-work batches once per minute did not keep up with this profile. The next profile needs tuned bounded worker budgets, opportunistic maintenance with cron recovery, and better catch-up paging/egress measurements. The live latency tail also needs explanation and improvement.

The harness refuses an unrecorded branch/Function combination. It measures append acknowledgments and observed live delivery, follows durable SSE checkpoints through rotations, samples frozen/local/outbox backlog every 30 seconds, forces bounded sealing after the workload, and compares exact binary records and producer order during full replay. A run fails on lost/duplicate/reordered records, failed requests, buffer/record bounds, missing live data, or an undrained sealing backlog. Raw JSON reports are saved under ignored `qualification-results/`; promote reviewed reports here with their context. The `Deployed Neon load qualification` manual GitHub workflow provisions and removes its own environment and retains the reports as artifacts.

Live latency is measured from the client starting the append through that client observing its payload, so it includes network transit and duplicates across readers. Database connection counts include other activity on the branch and do not measure per-isolate memory or pool queues. Add those measurements before treating this as complete production qualification.

That ten-minute harness verified durable record identities/order and live checkpoint coverage, but did not independently compare every reader's complete live byte sequence. The revised harness adds an ordered rolling SHA-256 per reader and compares it with the corresponding exact durable replay, using constant per-reader checksum state. Missing, duplicate, reordered, or foreign live bytes now fail that check even if a final checkpoint advanced. Reports containing `liveVerification` distinguish this stronger gate from earlier evidence.

The stronger live-byte harness passed a 75-second probe across SSE rotations on the same recorded payload deployment. All 16 readers' ordered SHA-256 digests matched their corresponding durable replay; see `2026-11-22-live-digests-75.json`. This is focused harness/delivery evidence. It does not retroactively add that gate to the earlier ten-minute report or substitute for a longer strict-byte soak.
