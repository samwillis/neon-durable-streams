# Stopped-Function in-place restore

An in-place database rollback can restore a serving epoch remembered by an older runtime. The database guard therefore supplements a stopped-ingress cutover. It cannot make an old runtime safe to leave running across rollback. The library's recovery APIs use data-plane credentials; the operator's separate deployment workflow controls Functions, triggers, and the Neon restore operation.

This procedure deliberately rolls back appends, producer sequence state, and acknowledgments after the chosen recovery point. Clients and downstream receivers must reconcile checkpoints and side effects. External webhook effects remain at least once. Retain the current database state, immutable objects, and external wrapping keys according to the consuming application's recovery policy.

## Cutover

1. Record the exact project, target branch, installation UUID, serving epoch, compatible binary/schema version, object-store identity, and recovery WAL LSN or timestamp. Confirm that the chosen recovery point remains available. Preserve external wrapping keys and the prior deployment configuration outside the database being rolled back.
2. Block public ingress and pause scheduled/application workers. For the Neon Function profile, remove or disable its triggers. Call `beginRecovery` against the current database with the inspected UUID/epoch to fence transactions and live sessions. Drain active readers and in-flight work, then stop every serving runtime. The qualification fixture deletes both of its owned Functions, verifies an empty Function/trigger list, and allows six seconds for the documented five-second SIGINT/forced-stop window before restoring. A consumer using additional runtimes or ingress routes must stop those too. See [Neon runtime limits](https://neon.com/docs/compute/functions/reference/runtime-limits.md).
3. Close old database pools. Restore only the intended branch from its own recorded WAL position or timestamp. When restoring a branch from itself, Neon requires `preserve_under_name`. Give that preserved history a unique recorded name before issuing the request. If the response is ambiguous, inspect branch/control-plane state rather than blindly issuing another restore.
4. Keep ingress and workers stopped. Open fresh administrative connections and inspect the restored installation. Run compatible explicit migrations if needed. A recovery token created before rollback may now be stale; create and persist a new operation ID for `beginRecovery` against the restored UUID/epoch. The resulting epoch must differ from the restored epoch. Never use migration binding options to bypass this recovery.
5. Repeatedly call `verifyRecovery` with finite batches, the actual target Object Storage adapter, and the external wrapping keyring. Every reachable restored sealed manifest must resolve to the exact verified bytes. Retired unreachable manifests may outlive their collected objects under the declared recovery policy. A missing object, wrong environment, unavailable key, or stale verification token leaves the installation quiesced. Repair the resource and resume verification before proceeding.
6. Call `finishRecovery` only after verification completes. It refuses active old-epoch reader leases and replay pins, resets abandoned claims, fences restored wake tokens, and schedules subscription work. A lost activation response can be retried with the same operation token.
7. Deploy fresh instances with the verified branch/storage bindings and external keys. Give the rollout a new `DS_DEPLOYMENT_ID`, even when its code hash is unchanged. Verify authenticated `ready: true` health with both expected identifiers, exact binary/JSON/fork replay, producer deduplication, Realtime delivery of a new append, and rejection of pre-restore callback tokens. Re-enable scheduled maintenance and reopen public ingress only after these checks. Reconnect live clients from reconciled durable offsets; a checkpoint beyond the rolled-back tail is rejected.

Use the [operations contract](operations-v1.md) for the recovery API example and the [payload contract](realtime-payload-v1.md) for bounded live-reader fencing. The workflow should retain an audit record of the selected recovery point, operation IDs, verification result, deployed artifact, and cutover checks, without credentials or callback tokens.

## Preserved history and Object Storage

Neon self-restore makes the preserved history a parent of the restored branch. A branch with children cannot have an expiry. Test tooling records both exact names before restore, expires the restored child, deletes leaves before parents, and uses a scheduled janitor for runner loss. Consumer backup retention is an operator policy; the qualification fixture's cleanup is not a recommendation to delete production recovery history immediately.

Current public Neon documentation says database PITR leaves Object Storage unchanged. Schema 0007 relies on coordinated provider recovery or matching object backups to restore every reachable immutable key, including keys deleted after the recovery point. Collection is disabled by default. The ordinary CI drill retains its witness objects and does not prove recovery of a previously deleted reachable key. Earlier schema-0006 physical-collection restore reports used application retention windows and remain historical evidence; they do not certify the future provider capability.

## Executable evidence

`test/recovery/inplace.test.ts` provisions its own isolated branch from the non-expiring test parent. It deploys the real consumer Function, cron, and HTTPS receiver fixture; writes binary and exact-number JSON data; creates a fork and a claimed pull wake; records a flushed WAL LSN; then observes a later append through actual Realtime/SSE. One HOT frame is sealed only after that recovery point. It pauses scheduling, quiesces the current epoch, drains the live reader, removes the Functions, and requests a real self-restore. It then verifies the restored epoch, HOT frame and sealed objects, activates a new epoch, redeploys fresh instances, and checks public protocol continuity, restored Realtime delivery, and old-token fencing. The current fixture also awaits a separate raw append observer before the post-restore write and requires its exact committed payload/end offset, independently of SSE setup catch-up or periodic SQL fallback.

The fixture rejects unrecorded targets and never restores its parent or the coordinator branch. A cleanup ledger records the target and preserved names before allocation/restore, including the ambiguous-response window. CI always attempts cleanup, and the janitor recognizes the fixture's reserved branch names. Its sanitized result is retained as `qualification-results/inplace-restore.json`. The final local run passed with the expected test-source hash, three verified sealed chunks, restored HOT replay, an unexpired token explicitly fenced by recovery, discarded-offset rejection, new Realtime/SSE delivery, and cron resumed after public validation. See the [recorded result](qualification/2026-11-22-inplace-restore.json) and [readiness trace](qualification/2026-11-22-inplace-readiness.json). Those reports retain their pre-commit source/dirty metadata, exact bundle and test hashes. Exact-head CI is a separate required gate. Larger installations and broader restore/fault profiles remain unqualified.


Post-restore Function HTTP readiness and Realtime query readiness are separate checks. The fixture allows at most 180 seconds for initial Realtime readiness, closing timed-out observers and retrying fresh subscriptions. It retries only initial snapshot timeouts; identity, authorization, and SQL failures remain immediate failures. Once the raw observer is ready, it issues the append and independently requires the committed payload within 30 seconds; public SSE still has its separate 45-second bound. Readiness attempt durations are recorded as `restoredRealtimeReadiness`. These startup bounds are qualification budgets, not an availability or recovery-time guarantee.
